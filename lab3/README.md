# Лабораторна робота 3. Синхронізація потоків: producer—consumer

Мова: C, середовище: Linux.

## Мета

Побачити на власних програмах, що відбувається, коли кілька потоків працюють зі спільними даними:

- як втрачаються оновлення спільної змінної і як ThreadSanitizer знаходить data race;
- скільки «коштує» м'ютекс і як від нього залежить швидкість;
- як потоки чекають один на одного через умовні змінні і чому `pthread_cond_wait` завжди викликають у циклі, який перевіряє умову;
- як виникає взаємоблокування, як побачити, хто кого чекає, і як його усунути порядком захоплення м'ютексів.

Теорія — підручник OSTEP (Operating Systems: Three Easy Pieces), розділи вказано в кожній частині.

## Середовище

Та сама Linux-VM, що й у ЛР2, щонайменше з 2 vCPU. Додатково потрібні `gdb` і налагоджувальна інформація glibc:

```sh
sudo apt install gdb libc6-dbg
```

Скопіюйте каталог `lab3` у VM. Якщо в ЛР2 ви користувалися Vagrant, найпростіше покласти `lab3` усередину каталогу `lab2` на своєму комп'ютері: у VM він з'явиться як `/vagrant/lab3`.

Перевірка:

```sh
cd lab3
sh check_env.sh
```

Усі рядки мають починатися з `ok`. Скрипт також пробує скомпілювати програму з ThreadSanitizer і переконатися, що він ловить data race.

`make` у каталозі `lab3` збирає кожну програму у двох версіях: звичайну (`part1-race/counter`) і з ThreadSanitizer (`part1-race/counter-tsan`). Після кожної зміни коду запускайте `make` знову, інакше запуститься стара версія. Час вимірюйте лише на звичайній версії: TSan сповільнює програму в рази.

Якщо програма з TSan одразу падає з `FATAL: ThreadSanitizer: unexpected memory mapping`, виконайте один раз після кожного запуску VM:

```sh
sudo sysctl vm.mmap_rnd_bits=28
```

## Довідка: потоки в C

| Що                                        | Як                                                                |
| ----------------------------------------- | ----------------------------------------------------------------- |
| Запустити потік, який виконає `f(arg)`    | `pthread_create(&t, NULL, f, arg)`, де `f` - `void* f(void *arg)` |
| Дочекатися завершення потоку              | `pthread_join(t, NULL)`                                           |
| Захопити й відпустити м'ютекс             | `pthread_mutex_lock(&m)`, `pthread_mutex_unlock(&m)`              |
| Чекати на умовній змінній                 | `pthread_cond_wait(&cv, &m)`                                      |
| Розбудити один або всі потоки, що чекають | `pthread_cond_signal(&cv)`, `pthread_cond_broadcast(&cv)`         |
| Семафор                                   | `sem_t`, `sem_wait(&s)`, `sem_post(&s)`                           |

Що трапиться в каркасах:

- `void *(*f)(void *)` — покажчик на функцію потоку.
- `*(int *)arg` — потік отримує адресу аргументу; приведення повертає їй тип. Змінна за цією адресою має існувати, доки потік працює.
- `(void)x;` — прибирає попередження про невикористану змінну.
- М'ютекс ініціалізують константою `PTHREAD_MUTEX_INITIALIZER` в оголошенні або викликом `pthread_mutex_init`. Умовні змінні так само.
- `pthread_mutex_unlock` потрібен на кожному шляху виходу з функції.
- Функції `pthread_*` при помилці повертають код помилки, тому в коді `strerror(err)`, а не `perror`.
- Довідка: `man pthread_create`, `man pthread_mutex_lock`, `man pthread_cond_wait`, `man sem_wait`.

## Додаткова інформація

- На захисті ви повинні вміти пояснити кожен рядок свого коду і кожне число у своїх відповідях. Те, що ви не можете пояснити, не зараховується.
- Усі виміри робіть у своїй VM і наводьте свої числа.
- Програма, що зависла, — очікуваний результат у частині 3 і в бонусі. Запускайте такі програми через `timeout 10 ...`: він завершить програму через 10 секунд і поверне код 124. Ctrl+C теж працює.
- Те, що програма кілька разів відпрацювала правильно, не доводить, що в ній немає race condition чи взаємоблокування. Тому, крім запусків, у кожній частині потрібне пояснення, чому код правильний.
